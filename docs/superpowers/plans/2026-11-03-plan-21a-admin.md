# План 21a: Адмінпанель — статистика, бан, видалення вікторин, запитань і призів (беклог #23)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Мета:** мінімальна адмінка на `/admin` для адмінів зі змінної `ADMIN_EMAILS`:
- статистика (лише цифри й топ-10);
- список користувачів із пошуком, бан і розбан;
- видалення будь-якої вікторини й окремого запитання в чужій вікторині;
- видалення призів зі складу й нагород з вітрини будь-кого;
- журнал дій адмінів.

**Spec:** `docs/superpowers/specs/2026-11-01-admin-panel-design.md`. Читати повністю: «Що будуємо», «Мої рішення», «Рішення після builder-check», «Не цілі», «Анти-цілі», «Обмеження», «Залишено на будівника». Призи й вітрина: `docs/superpowers/specs/2026-11-01-prizes-showcase-design.md`.

**Передумова:** у `main` уже все до 20a (Web Push) і перегляду призу. Міграції до `0026_push` зайняті, тож наша — **`0027_admin`** (journal idx 27). Гачки для адмінки вже є:
- `notHidden(column)` у `apps/server/src/feed-store.ts` (зараз `sql\`true\``). Його вже кличуть стрічка, лайки-картки й календар;
- `listAllPrizes`, `deletePrize(db, manager, id, null)` і `deleteAward` у `apps/server/src/prizes.ts`.

**Стан гри не змінюється: `GAME_STATE_VERSION` лишається 22.** Закриття кімнат забаненого ведучого йде наявними шляхами: `end()` рушія і внутрішнім `close()` менеджера. `GameState`, `SavedRoom` і рушій не змінюються. Пуш у `main` не обриває живих ігор.

**Архітектура:**
- **Shared** (`packages/shared/src/admin.ts`): типи відповідей адмінки, схеми запитів, константи.
- **Сервер:**
  - `config.ts` → `adminEmails(env)`;
  - `admin.ts` — `isAdminEmail`, `isAdmin(db, emails, userId)`;
  - таблиці `user_ban` і `admin_action` (міграція `0027_admin`);
  - `bans.ts` — `isBanned`, `banUser`, `unbanUser`, `logAction`, `banNotice`; справжній `notHidden`;
  - бан перевіряють три місця: `currentUser` (кожне читання сесії), хук Better Auth `session.create.before` (будь-який вхід) і проксі `/api/auth/*` (переписує редирект Google на `/login?error=account_banned`);
  - `RoomManager.closeHostedBy(userId)` — живі кімнати забаненого;
  - `quiz-remove.ts` — чисте видалення запитання; `quizzes.ts` — `ownerId: string | null`;
  - `admin-store.ts` — статистика, списки, картка людини, журнал;
  - `admin-routes.ts` — усі `/api/admin/*`; для не-адміна 404 `{ error: 'not_found' }`, як для неіснуючого маршруту.
- **Веб:** `apps/web/src/admin/*`. Сторінка `/admin/*` має вкладки «Статистика», «Користувачі», «Вікторини», «Журнал». Вхід — посилання «Адмінка» в `/profile`, яке бачать лише адміни. **Меню не змінюється: сім пунктів.**

**Технології:** TypeScript, zod, vitest, Fastify (+ `@fastify/rate-limit`), Better Auth 1.7 (`databaseHooks`, `APIError` з `better-auth/api`), Drizzle + drizzle-kit + PGlite, React 19 + Vite, Testing Library (jsdom), Playwright. `node:async_hooks` (`AsyncLocalStorage`). Нових залежностей немає.

## Рішення (там, де специфікація лишила місце будівникові)

- **Хто адмін:**
  - `ADMIN_EMAILS` — адреси через кому; кожна з `trim()` і `toLowerCase()`, порожні відкидаються;
  - адмін — той, чий `user.email` (`trim` + `toLowerCase`) є в наборі **і** `user.email_verified = true`;
  - змінної немає чи вона порожня → адмінів немає, сервер стартує, посилання «Адмінка» ніде не з'являється, `/api/admin/*` → 404 усім;
  - перевірка йде щоразу з бази (`isAdmin(db, emails, userId)`), без кешу. Порожній набір не робить запиту.
- **Жодної справжньої адреси в коді, тестах, фікстурах, коментарях, `.env.example`, `render.yaml` чи цьому плані.** Тести беруть адреси, які генерує `signUp` (`…@example.com`), і вмикають `email_verified` прямо в базі. e2e — вигадану `admin21a@example.com`.
- **`/api/me`** віддає `{ id, name, email, admin: boolean }`. Поле `admin` — лише про себе, про інших нічого не каже. Вебу воно потрібне, щоб показати посилання.
- **Приховування адмінки:**
  - кожен `/api/admin/*` спершу кличе `requireAdmin`; аноніма й не-адміна зустрічає `404 { error: 'not_found' }`. Тіло те саме, що в `setNotFoundHandler` для невідомого `/api/...`;
  - перевірка йде **до** розбору тіла й параметрів, тож невалідний запит від не-адміна теж дає 404, а не 400;
  - обмеження частоти рахує лише адмінів (`allowList` пропускає не-адмінів), тож 429 існування маршруту не видає. Ліміти: читання 120/хв, запис 30/хв на адміна (`admin-read:<id>`, `admin-write:<id>`);
  - веб `/admin` для не-адміна робить `<Navigate to="/" replace />`, як маршрут `*`.
- **Схема бану:**
  - `user_ban (user_id PK FK→user cascade, reason text null, banned_by text null FK→user set null, banned_at timestamptz not null)`;
  - розбан видаляє рядок, історію тримає журнал;
  - бан безстроковий;
  - причина: `trim`, `''` → `null`, щонайбільше 500 символів. Її бачать лише адміни: у картці людини й журналі.
- **Журнал:** `admin_action`. Колонки:
  - `id uuid`, `at timestamptz`;
  - `admin_id text null FK→user set null`;
  - `admin_label text` — нікнейм адміна на ту мить;
  - `kind text` — `ban | unban | quiz_delete | question_delete | prize_delete | award_delete`;
  - `target_user_id text null` без FK;
  - `target_label text` — нікнейм потерпілого на ту мить;
  - `details jsonb`.

  Індекс `(at desc)`. Email у журнал не пишеться.
- **«Нічого не стирається фізично, крім вікторин і запитань».** Призи й нагороди адмін видаляє наявними `deletePrize(…, null)` і `deleteAward`, тобто рядок зникає. Тому `details` журналу зберігає **повний знімок** змісту (`PrizeContent`, для нагороди ще `quizTitle`), і слід лишається. Файли фото в R2 не видаляються.
- **Нагорода й титул.** Якщо `content.title` видаленої нагороди дорівнює чинному `user_title.text` її власника, рядок `user_title` теж видаляється. Інакше образливий титул лишився б біля ніку.
- **Що бан ховає від інших** (`notHidden(col)` = `not exists (select 1 from user_ban where user_id = col)`):
  - `publicProfile`, `/api/profiles/:id/achievements`, `/api/me/versus/:id`, `PUT /api/me/friends/:id` → 404, як для неіснуючого;
  - `friendsOf` (обидва запити), `searchProfiles`, `findByNickname` — без забанених;
  - стрічка, лайки-картки, календар — уже через `notHidden`. Додатково запити участі забанених у чужих подіях (`calendar-store.ts`, список `hosted`) і адресати пушів (`push.ts`: `participants` і `remindDue` для подій забаненого ведучого);
  - `/api/me/invites` пропускає кімнати забаненого ведучого;
  - **минула історія не змінюється:** `participant.nickname`, `game.*`, подіуми, `prize_award.nickname` не чіпаємо;
  - власні сторінки забаненого не важать: він не може увійти.
- **Живі кімнати забаненого** (`hostUserId === userId`, і ведучий, і автор автопілота) закриваються в мить бану:
  - `lobby` → `close(room)`: гравці бачать «Цієї гри вже немає…», бо гри ще не було;
  - гра йде → `end()` рушія: фаза `finished`, гравці бачать «Гру завершено», результат пишеться як звичайне завершення;
  - `finished` → без змін.
  Ролі гостя-гравця в чужих кімнатах це не стосується (специфікація: гостей не блокуємо).
- **Вхід забаненого:**
  - `email/пароль`: хук кидає `APIError('FORBIDDEN', { code: 'ACCOUNT_BANNED', message: 'ACCOUNT_BANNED' })` → 403, cookie немає. Веб: `AUTH_CODES` → `account_banned` → «Акаунт заблоковано.»;
  - Google: той самий хук. Кинуту помилку Better Auth перетворює на свій редирект, тому хук ще ставить `banNotice.getStore().banned = true` (`AsyncLocalStorage`, яким проксі обгортає `auth.handler`). Проксі для 3xx з цим прапорцем переписує `Location` на `/login?error=account_banned`. Login показує той самий текст.
- **Видалення вікторини адміном** — `deleteQuiz(db, null, id)`, той самий шлях, що в автора: лайки ховаються, `calendar_event.quiz_id` → `null` (FK), `game.quiz_snapshot` лишається, жива кімната має свою копію.
- **Видалення запитання** (`quiz-remove.ts`, лише сервер):
  - видаляються запитання раундів (`questionsOf`, зокрема клітинки поля), питання на виживання (`trials`), запасні вікторини (`spares`) і категорій поля (`category.spares`);
  - **запитання дуелей окремо не видаляються** (`not_found`); веб показує їх лише для читання з підказкою, що прибрати їх можна тільки разом із вікториною;
  - якщо контейнер падає нижче мінімуму схеми, він іде цілком. Категорія поля < `LIMITS.minCategoryQuestions` → категорія; категорій < `LIMITS.minCategories` → раунд; класика чи бліц без запитань → раунд; фінал → раунд; «Ва-банк» < `minWipeoutQuestions`, «Вибування» < `minSurvivalQuestions`, «Мільйонер» < `minLadderQuestions` → раунд;
  - «Мільйонер»: разом із запитанням `i` йде `levels[i]`, із `safe` прибирається `i`, а індекси `> i` зменшуються на 1;
  - порожні `spares` → поле видаляється;
  - якщо після видалення `questionsOf` порожній → `last_question` (409). Кнопка неактивна з підказкою «Видали вікторину цілком»;
  - підсумок проходить `quizSchema.safeParse`. Якщо ні → 409 `question_locked`, і нічого не пишеться;
  - запис — у транзакції з `select … for update` рядка вікторини, далі `syncHiddenLikes`, `updated_at = now`;
  - сервер віддає вебу `effects: Record<questionId, RemovalEffect>`, тож підтвердження знає, чи піде весь раунд.
- **Статистика:**
  - користувачі: `count(user)`; нові — `user.created_at >= now − 7 / 30 діб`; онлайн — `profile.last_seen_at >= now − ONLINE_MS` (5 хв, з shared);
  - ігри: «живі» — `manager.rooms()` з `phase !== 'finished'` (і лобі, і гра); «сьогодні» — `game.status = 'finished'` і `finished_at >= kyivMidnight(now)`; 7 / 30 діб — `finished_at >= now − N діб`;
  - вікторини: `count(quiz)`;
  - топ-10: `game` (`finished`) `inner join quiz` за `quiz_id`, групування, `order by count desc, quiz.title asc`, `limit 10`. Ігри видалених вікторин не рахуються. Автор — нікнейм профілю.
- **Списки:**
  - сторінка `ADMIN_PAGE_SIZE = 50`, `page` з 1; `pages = max(1, ceil(total / 50))`;
  - користувачі: `order by user.created_at desc, user.id`; пошук `q` (2…100 символів після `trim`, коротший — без фільтра) — `profile.nickname ilike %q% or user.email ilike %q%`, `%`, `_`, `\` екрануються;

- **Приватність адмінки:** адмін бачить нік, email, дату реєстрації, лічильники, статус і причину бану, вміст вікторин, склад і вітрину. Сесій, IP, паролів, `account`, підписок і чужих «онлайн»-міток (крім загального числа) адмін не бачить.

## Що має зробити власник

Без цього код працює, але адмінів немає. Контролер проведе власника дашбордом Render крок за кроком, зі скриншотами.

1. **Render → сервіс `fam-quiz` → Environment → Add Environment Variable:**
   - Key: `ADMIN_EMAILS`;
   - Value: дві адреси адмінів через кому, без лапок (наприклад, `перша@адреса,друга@адреса`). Регістр і пробіли не важать.
2. **Save Changes** → Render перезапустить сервіс. Міграція `0027_admin` пройде сама під час запуску.
3. **Перевірка:** увійти через Google тим акаунтом → «Профіль» → посилання «Адмінка». Інший акаунт посилання не бачить, а `/admin` веде на головну.
4. **Нікуди більше** адреси не класти: ні в git, ні в `.env.example`, ні в `render.yaml`, ні в пам'ять, ні в повідомлення комітів. Локально (необов'язково) рядок можна вписати в `.env`, він не в git.
5. Акаунт email/пароль із тією самою адресою адміном **не стане**: у нього непідтверджена адреса. Входити треба через Google.

## Гачки на потім (не будуємо зараз)

- Ролі, крім «адмін», графіки, розсилки — не цілі.
- Видалення окремих запитань дуелей.
- Нові специфікації, що показують людей іншим, підключаються до `notHidden` (`feed-store.ts`), а видалення вікторини обробляють так само, як видалення автором.

## Глобальні обмеження

- **Адміни — лише з `ADMIN_EMAILS`** (кома, `trim`, без регістру) і лише з `email_verified = true`. Жодної справжньої адреси в репозиторії: він публічний. Без змінної адмінів немає, сервер стартує, посилання «Адмінка» приховане.
- **Кожен `/api/admin/*` перевіряє адміна на сервері** до будь-якого іншого коду. Для не-адміна й аноніма — `404 { error: 'not_found' }`, і 429 не буває.
